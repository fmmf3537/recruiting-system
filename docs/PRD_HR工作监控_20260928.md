# PRD：HR 工作负载与薄弱环节监控（admin）

> 版本：v0.1 评审稿  
> 日期：2026-09-28  
> 状态：待评审  
> 依赖澄清结论：过程+结果都要；按操作人归属；薄弱环节按招聘漏斗转化率；第一期仅 admin 可见。

---

## 1. 背景与目标

admin 需要像猎头公司管理猎头顾问一样，持续掌握每个 HR 的工作状态：今天/本周/本月做了多少事、推进是否有效、卡在哪个环节、谁需要辅导或调整分工。

现有系统已有候选人、职位、面试、Offer、沟通记录、阶段记录、操作日志、HR 积分等数据，但缺少一个**面向管理决策的 HR 个人工作台**：

- 不能只靠“ HR 积分”看结果，积分偏规则激励，不能解释“为什么弱”。
- 不能只靠全局统计看团队，需要下钻到“某个 HR 的某一天/某一周/某一月”。
- 需要把“过程工作量”和“结果转化”放在同一视图，避免只看忙碌不看产出。

### 1.1 业务目标

1. admin 能在 30 秒内回答：
   - 今天/本周/本月每个 HR 做了多少关键动作；
   - 谁的产出高、谁只是忙但转化差；
   - 哪个 HR 的薄弱环节在筛选、面试、Offer 还是入职。
2. 支持管理动作：
   - 横向对比 HR；
   - 下钻查看单个 HR 的明细；
   - 导出周/月报用于例会或绩效沟通。
3. 为二期打基础：
   - 目标管理（ quota / KPI ）；
   - 自动预警（连续低产、环节异常、超时未处理）；
   - 辅导记录与改进追踪。

### 1.2 非目标（第一期不做）

- 不做人脸/在线时长/键盘鼠标式监控。
- 不做 HR 自己填报日报（第一期完全基于系统行为数据）。
- 不做跨系统 IM/邮件外部分析。
- 不做复杂绩效公式配置后台（先固定指标口径，后续再配置化）。

## 2. 用户与权限

### 2.1 角色

| 角色 | 能力 |
|---|---|
| admin | 查看全部 HR 的日/周/月面板、排行榜、漏斗、明细、导出 |
| hr / member | 第一期不可见本功能；保留现有“我的积分/工作台” |
| hiring_manager / interviewer | 不可见 |

### 2.2 权限设计

- 新增权限点：`hr_workload:read`（仅 admin 默认拥有；admin 也可继续用 `*` 覆盖）。
- 后端所有新接口统一：`authenticate` + `requireMatrixPermission('hr_workload:read')`。
- 前端路由：`meta.requireAdmin = true`，菜单仅 admin 显示。
- 下钻候选人明细时仍复用 `CandidateVisibilityScope`；admin 天然全量，避免越权展示候选人敏感信息。

## 3. 核心口径

### 3.1 归属口径：按操作人

一个动作算给“实际做这个动作的人”：

| 指标 | 归属字段/依据 |
|---|---|
| 新增候选人 | `Candidate.createdById` |
| 沟通跟进 | `CommunicationLog.createdById` |
| 安排面试 | `Interview.createdById` |
| 阶段推进 | 优先 `OperationLog` 中阶段推进记录的操作人；历史数据退化用 `StageRecord.assigneeId` 近似 |
| Offer 创建/提交/审批/发送/结果 | 优先 `OperationLog` 的 offer 系列 action；无日志时用 `Offer.updatedAt + status/result` 近似 |
| 入职 | Offer `joined=true` 的操作日志；无日志时归属候选人创建人并标记“近似” |

> 设计原则：  
> **第一期允许“历史近似”，但从功能上线后必须写标准操作日志，保证后续越来越准。**

### 3.2 时间口径

支持三个周期，统一用同一个日期锚点：

| 周期 | 定义 |
|---|---|
| 日 | 所选自然日 00:00:00 - 23:59:59 |
| 周 | 所选日期所在自然周，周一到周日 |
| 月 | 所选日期所在自然月 |

时区：按服务器本地时区统计，前端展示 `YYYY-MM-DD`。

### 3.3 结果口径：招聘漏斗转化率

每个 HR 的漏斗按“操作人动作序列”聚合：

1. 新增候选人
2. 初筛通过
3. 面试完成
4. Offer 发送
5. Offer 接受
6. 入职

薄弱环节识别规则（第一期固定）：

- 计算每个环节转化率：`当前环节人数 / 上一环节人数`。
- 与团队均值比较，低于团队均值 20% 以上标为“偏弱”。
- 若样本量过小（上一环节 < 5），不判定强弱，只显示“样本不足”。

## 4. 指标体系

### 4.1 总览指标（日/周/月共用）

| 指标 | 说明 |
|---|---|
| 活跃 HR 数 | 周期内有任一关键动作的 HR 数 |
| 新增候选人 | HR 新创建的候选人数 |
| 沟通跟进次数 | 沟通记录创建数 |
| 安排面试数 | 面试创建数 |
| 完成面试数 | 面试标记完成数 |
| Offer 发送数 | Offer 标记已发送数 |
| Offer 接受数 | result=accepted 数 |
| 入职数 | joined=true 数 |
| 平均招聘周期 | 候选人创建到入职的平均天数 |
| 薄弱环节 TOP | 按偏离团队均值排序展示前 3 个 HR-环节组合 |

### 4.2 HR 个人明细指标

| 分组 | 指标 |
|---|---|
| 过程量 | 新增候选人、沟通次数、安排面试、完成面试、Offer 动作次数、阶段推进次数 |
| 结果量 | 初筛通过、复试/终面推进、Offer 发送、Offer 接受、入职 |
| 转化率 | 初筛通过率、面试完成率、Offer 接受率、入职率 |
| 质量 | Offer 拒绝率、入职后 30 天留存（如无数据则显示“未接入”） |
| 及时性（展示项） | 面试后待评估数、跟进到期未处理数、阶段停留超时数 |

### 4.3 排行与分层

- 排行榜默认按“入职数”排序，可切换：新增候选人、安排面试、Offer 接受、入职。
- 增加“忙碌但低效”提示：
  - 过程量高于团队均值 20%；
  - 入职率低于团队均值 20%；
  - 标记为“需关注转化”。

## 5. 页面设计

### 5.1 入口

- 菜单位置：`数据报表` 下新增子页：`HR 工作监控`。
- 路由：`/stats/hr-workload`。
- 权限：仅 admin 可见。

### 5.2 页面结构

1. **筛选区**
   - 周期：日 / 周 / 月
   - 日期锚点：日期选择器
   - 部门：全部 / 部门字典
   - HR：全部 / 指定 HR

2. **总览卡片**
   - 活跃 HR 数
   - 新增候选人
   - 安排面试
   - Offer 发送
   - Offer 接受
   - 入职
   - 平均招聘周期
   - 薄弱环节数

3. **排行榜表格**
   - HR 姓名 / 部门
   - 新增候选人
   - 沟通次数
   - 安排面试
   - Offer 发送 / 接受 / 入职
   - 初筛通过率 / Offer 接受率 / 入职率
   - 状态标签：正常 / 需关注转化 / 样本不足
   - 操作：查看详情 / 导出该 HR 明细

4. **对比图区**
   - HR 过程量柱状图
   - HR 入职率排行
   - 团队漏斗图
   - 薄弱环节分布图

5. **个人下钻抽屉/详情页**
   - 周期趋势图
   - 个人漏斗
   - 关键动作时间线
   - 候选人明细列表（只展示必要字段，敏感字段按现有权限脱敏）
   - 系统给出的薄弱环节解释：
     - 例：`近 4 周 Offer 接受率 25%，团队均值 48%，建议检查薪资沟通与期望管理。`

## 6. API 设计

### 6.1 总览

`GET /api/hr-workload/overview`

Query：

```ts
{
  period: 'day' | 'week' | 'month';
  date: string;        // YYYY-MM-DD
  department?: string;
  hrId?: string;
}
```

Response：

```ts
{
  success: true;
  data: {
    range: { start: string; end: string };
    summary: {
      activeHrCount: number;
      newCandidates: number;
      communications: number;
      interviewsScheduled: number;
      interviewsCompleted: number;
      offersSent: number;
      offersAccepted: number;
      joined: number;
      avgCycleDays: number | null;
      weakPointCount: number;
    };
    rows: Array<{
      hrId: string;
      hrName: string;
      department: string | null;
      process: Record<string, number>;
      result: Record<string, number>;
      rates: Record<string, number | null>;
      status: 'normal' | 'need_attention' | 'insufficient_sample';
      weakPoints: Array<{ stage: string; rate: number | null; teamRate: number | null }>;
    }>;
  };
}
```

### 6.2 个人详情

`GET /api/hr-workload/users/:hrId`

Query 同 overview，额外支持：

```ts
{
  includeTimeline?: boolean;
  includeCandidates?: boolean;
}
```

### 6.3 导出

`GET /api/hr-workload/export`

- 支持 xlsx。
- 权限同 overview。
- 导出写 `OperationLog`：`hr_workload_export`。

## 7. 数据实现方案

### 7.1 第一期：实时计算 + 缓存

优点：不改 schema、上线快。  
缺点：月维度全量统计可能慢。

策略：

- 汇总查询集中在 `server/src/services/hr-workload.service.ts`。
- 使用 Prisma + 必要 `$queryRaw`。
- 缓存：
  - overview 缓存 60 秒；
  - export 不走缓存；
  - 缓存 key 包含 period/date/department/hrId。

### 7.2 第二期：每日快照表

建议新增 `hr_workload_daily_snapshot`：

| 字段 | 说明 |
|---|---|
| id | cuid |
| hrId | HR |
| date | 日期 |
| metrics | Json，过程/结果/转化率 |
| createdAt / updatedAt | 审计 |

由 node-cron 每天凌晨生成前一天快照；月/周读快照聚合。第一期不做。

### 7.3 操作日志补齐

为保证“按操作人归属”长期准确，第一期开发时需要同步检查并补齐这些 action：

- 候选人阶段推进
- 面试创建 / 更新 / 取消 / 完成
- Offer 创建 / 提交 / 审批 / 驳回 / 发送 / 接受 / 拒绝 / 入职
- 沟通记录创建

缺口处理原则：

- 已有 action 的只复用；
- 缺 action 的在对应 service 补 `OperationLog`，失败不阻断主流程；
- 不在本需求里大规模回刷历史日志。

## 8. 薄弱环节判定逻辑

### 8.1 输入

- 当前 HR 的漏斗转化率
- 团队同周期均值
- 样本量

### 8.2 规则

```text
若上一环节样本数 < 5：样本不足，不判强弱。
若 HR 转化率 < 团队均值 * 0.8：标记偏弱。
若 HR 过程量 > 团队均值 * 1.2 且入职率 < 团队均值 * 0.8：标记“忙碌但低效”。
```

### 8.3 展示文案

- `筛选通过率偏低`
- `面试完成率偏低`
- `Offer 接受率偏低`
- `入职率偏低`
- `样本不足`
- `忙碌但低效`

---

## 9. 异常与边界

1. 周期内无数据：显示空态，不显示 0 除错误。
2. 分母为 0：转化率显示 `null`，前端显示 `—`。
3. HR 已删除/禁用：历史数据仍保留，名称显示原姓名快照或 `已删除用户`。
4. 候选人被匿名化：保留统计字段，不展示姓名/手机号。
5. 跨部门 HR：部门为空时进入“全部部门”统计；部门筛选时按 `User.department` 过滤。
6. 数据延迟：实时计算最多依赖 60 秒缓存；导出时实时查库。

---

## 10. 安全与合规

- 仅 admin 可见。
- 导出写操作日志。
- 下钻候选人列表不展示手机号/邮箱明文，除非现有候选人详情权限允许。
- 不在排行榜展示候选人敏感信息，只展示数量与转化率。

## 11. 验收标准

### 11.1 功能验收

1. admin 可进入 `/stats/hr-workload`。
2. 日/周/月切换后，summary、排行榜、图表、详情全部刷新。
3. 选择部门后，只统计该部门 HR。
4. 点击某个 HR 可看到个人漏斗、趋势、关键动作时间线。
5. 导出 xlsx 内容与页面一致。
6. hr / hiring_manager / interviewer 访问接口返回 403，前端无菜单。

### 11.2 数据验收

1. 新增候选人数量与候选人列表按创建人筛选结果一致。
2. 安排面试数量与面试列表按创建人筛选结果一致。
3. Offer 接受 / 入职数量与 Offer 状态一致。
4. 分母为 0 时不报错。
5. 低样本不误判薄弱环节。

### 11.3 性能验收

1. 月维度 overview P95 < 2s（有缓存时 < 300ms）。
2. 单次导出 1 万行内可完成。
3. 不引入 N+1 查询。
