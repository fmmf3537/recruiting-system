## 2. 上下文（已实读源码）

### 2.1 通知中心（`server/src/routes/notification.ts`）

```
GET  /api/notifications            列表（登录用户）
GET  /api/notifications/unread-count  未读数
POST /api/notifications/mark-read  标记单条已读  { notificationId: cuid }
POST /api/notifications/mark-all-read  全部已读
```

### 2.2 标签（`server/src/routes/tags.ts`）

```

POST /api/tags/init-presets       初始化预设（admin）
PATCH /api/tags/:id               更新（partial）
DELETE /api/tags/:id              删除
```

### 2.3 字典（`server/src/routes/dictionaries.ts`）

```
GET  /api/dictionaries            列表（登录用户，category/includeDisabled 筛选）
GET  /api/dictionaries/categories 分类清单（登录用户）
POST /api/dictionaries/import     批量导入（admin，multer file）
POST /api/dictionaries            创建（admin）{ category ≥1, code?, name ≥1, ... }
PATCH /api/dictionaries/:id       更新（admin）
DELETE /api/dictionaries/:id      删除（admin）
```

## 3. 必读约束

### 3.1 反直觉点

1. **通知是系统生成**：e2e 环境不一定有通知记录 → 用例设计成「读接口 + 幂等操作」，不依赖已有数据。
2. **标签 color 必须 #RRGGBB**：zod regex 严格校验（测试用非法值断言 400）。
3. **字典创建仅 admin**：`authorize('admin')` —— 非 admin（hr）403。
4. **字典编码 code 可选**：创建时 category + name 是必填。
5. **字典分类动态化**：`GET /categories` 返回数组，供前端 radio。

### 3.2 不需要 mock

本 e2e 是真接口测试（不 mock）。需要：
- 后端在跑（PG + Redis + backend）
- `.auth/admin.json` 存在（admin token）

## 5. 关键决策点

### 5.1 为什么拆 3 个 spec 文件
三个模块路由独立、语义独立，拆开利于失败定位与维护（与「一模块一 spec」惯例一致）。

### 5.2 为什么通知用例不依赖已有数据
通知由系统事件生成，e2e 基础环境无固定 fixture。设计为读接口 + 幂等操作（mark-all-read 对空列表也是 200）。

### 5.3 为什么 mark-read 用 [400,404] 双断言
`markReadSchema` 校验 cuid 格式（400）；若 fake id 是合法 cuid 格式（`clxxx...`），service 查不到 → 404。用包容断言避免耦合细节。

### 5.4 不做的
- 不改后端三个 service（均有集成测试：notifications/stats 等）
- 不改前端对应 api 文件
- 不改 prisma schema / migrations
- 不跑验收命令
