## 3. 必读约束

### 3.1 反直觉点（显式标注）
1. **createCandidate 不创建初始 StageRecord**：候选人的「第一条」StageRecord 是在 advanceStage 时才产生，不是创建时。因此首次推进检测必须查 `stageRecord.count({where:{candidateId}}) === 0`。
2. **completeInterview / updateOffer / markOfferSent 均无 userId 透传**：completeInterview 用 Interview.createdById；updateOffer 用 candidate.createdById；markOfferSent 有 userId 参数（ actor）。
3. **joined +50 双路径去重**：manual advanceStage 和 offer auto-advance 都会创建「入职」StageRecord。统一记给 `candidate.createdById`，P2002 去重保证只记一次。
4. **字典 description 存分值**：`hr_score_rule` 的 description 存 `"2"` / `"-10"` 等整数字符串；parseInt 失败 fallback 常量默认值。
5. **负分归属 candidate.createdById**：与正分「动作执行人」不同，负分约束的是招聘结果所有者。

### 3.2 安全与幂等
- P2002（唯一约束冲突）= 已记分，直接静默跳过，不抛错。
- 发射器内部任何未预期错误都必须被捕获、仅记日志、绝不抛到调用方。
- 业务 service 中的发射调用也要再包一层 `try/catch`，形成**双重 fail-safe**。

### 4.1 `server/prisma/schema.prisma`（条件修改）
文件末尾区域追加两个 model + 一个 relation 行（`User` 模型追加 `hrScoreEvents HrScoreEvent[]` 和 `hrScoreSnapshots HrScoreSnapshot[]`，仅关系字段，不改既有字段）。

```prisma
model HrScoreEvent {
  id         String   @id @default(cuid())
  userId     String
  user       User     @relation(fields: [userId], references: [id])
  ruleCode   String   // 对应 hr_score_rule.code
  category   String   // business / process
  points     Int
  targetType String?  // Candidate / Interview / Offer / StageRecord
  targetId   String?
  remark     String?
  bizDate    DateTime @db.Date // 归属业务日期
  createdAt  DateTime @default(now())

  @@unique([userId, ruleCode, targetType, targetId]) // 幂等防重（nullable target 列允许多行 NULL）
  @@index([userId, bizDate])
  @@map("hr_score_event")
}

model HrScoreSnapshot {
  id           String   @id @default(cuid())
  userId       String
  user         User     @relation(fields: [userId], references: [id])
  periodType   String   // day / week / month / quarter / year
  periodStart  DateTime @db.Date
  businessPts  Int
  processPts   Int
  totalScore   Float    // 权重快照（F4-S2 写入）
  rank         Int?
  createdAt    DateTime @default(now())

  @@unique([userId, periodType, periodStart])
  @@map("hr_score_snapshot")
}
```

## 5. 关键决策点

### 5.1 joined +50 双路径去重实现
manual advance 与 offer auto-advance 都记给 `candidate.createdById`，`@@unique([userId, ruleCode, targetType, targetId])` 保证只存一行。如果 offer auto-advance 先写，advanceStage 后写 → P2002 静默跳过；反之亦然。

### 5.2 首次推进计数时机
`prisma.stageRecord.count({where:{candidateId}})` 放在 `$transaction` 之前读取。并发场景下可能出现两个推进同时读取到 count=0，但 P2002 唯一约束（userId+code+targetType+targetId）对同一 operatedById 只保留一条；不同 operatedById 会写两条，但业务上几乎不可能同一候选人在同一毫秒被两个不同 HR 同时推进。若要求绝对严格，可在发射前再查一次，但没必要。

### 5.3 不做清单
- 不做聚合/报表/cron（F4-S2 负责）。
- 不做前端（F4-C 负责）。
- 不新增路由/controller/集成测试（无新接口）。
- 不 git commit、不跑验收命令。
