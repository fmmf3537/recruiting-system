# 切片自动化接力 · 使用手册

> 版本：v1.0（2026-09-02）
> 适用：任何已接入 dev-slice-loop 流水线的项目
> 样板项目：`C:\Users\fmmf\kimi\recruiting-system`（本仓库即第一份完整样板）

---

## 1. 这是什么

把「人定需求 → Kimi 起草切片提示词 → 执行 agent（opencode）写代码 → Kimi 亲手验收 → 修订闭环 → 提交」固化成无人值守流水线。

- **单切片 6 阶段**：起草提示词 → 提交提示词并启动执行器 → 轮询 → 审核（亲手重跑验收）→ 修订闭环 → 通过收尾（业务 commit）
- **接力机制**：一个 cron 定时任务（`local_conversation` Automation），每次触发都是全新一轮、全新步骤预算，自动从中断点继续，彻底解决「单轮步骤上限」
- **进度三处落盘**：git 提交历史 + `AGENTS.md` 进度行 + `docs/cursor-prompts/` 提示词档案——任何中断（重启、删除任务、隔天再跑）都无损恢复

## 2. 新项目启用流程

### 阶段一：一次性接入（每个项目只做一遍，约 10~15 分钟）

**你说**（在目标项目的工作区里）：`接入切片自动化流程`

**Kimi 做**：
1. 复制 6 个 runner 脚本到该项目 `scripts/`，`.gitignore` 加 `logs/`
2. 核查执行器（opencode / Codex，全局安装，通常直接可用）
3. 亲手实测该项目的验收命令集与基线数字（每个项目不同，必须重测）
4. 确认切片计划目录（惯例 `docs/cursor-prompts/`），提交接入 commit

### 阶段二：定切片计划（每个功能阶段做一遍）

**你说**：给需求来源——`按这份 PRD 切` / `按这个开发计划切`

**Kimi 做**：分析需求 → 给出切片清单（范围 / 文件预算 / 顺序依据）→ **你确认或调整方案**（你的拍板点）

### 阶段三：启动自动接力（一句话）

**你说**：`建接力任务，自动跑`

**Kimi 做**：建 cron 定时任务（错开整点半点），提示词写死流水线规则、验收基线与停点清单。**建完即自动运行，无需再按任何启动键**。通常先手动跑第一个切片让流水线进入节奏。

### 阶段四：日常

- **自动**：每个触发点接力执行下一切片、验收、提交
- **你看**：每片完成有汇报；触顶 / 执行器故障由下一轮自动接上
- **你拍板**：遇到停点会停下等你（见 §4 停点清单）

### 阶段五：暂停 / 恢复 / 收尾（都是一句话）

| 你说 | 效果 |
|---|---|
| `停掉接力` | 禁用任务（任务与历史保留） |
| `恢复接力` | 重新启用，下个触发点自动跑 |
| `现在就跑一轮` | 不等时间表，立即手动触发 |
| `删掉接力` | 彻底删除任务定义 |
| （界面操作） | Kimi 桌面端定时任务面板也可直接开关 |

## 3. 无人值守的边界

**全自动的部分**：起草提示词 → 执行 → 轮询 → 亲手验收 → 修订 → commit → 进度同步。

**仍会停下等你的部分（特性，不是缺陷）**：
1. 安全敏感切片（如无鉴权公开接口）—— 专项复核
2. 数据库迁移 apply —— 迁移 SQL 由人工 review 后执行
3. 选型 / 取舍类决策 —— 不替你拍板
4. 收尾与生产部署 —— 合规确认、上线操作

**物理前提**：电脑开机、Kimi 桌面端运行中、执行器模型 API 额度充足。

---

## 4. 停点清单（写入每个接力任务的提示词）

- F5 类公开接口切片必须先人工安全复核
- 含 schema 变更的切片：迁移只生成 SQL，不执行 apply
- 基线数字（测试数 / lint 数 / type-check 数）只许持平或改善，恶化必须修订
- 红线：验收命令永远由审核方亲手重跑，不采信执行 agent 自报结果

---

## 5. 多项目并行注意

- 接力任务额度：cron 槽位 15 个，每项目 1 个，够 3~4 个项目并行
- 多项目任务的触发分钟要错开（避免同一分钟并发抢 CPU 与 API 额度）
- 执行器 CLI 与认证全局共享，新项目无需重装

## 6. 手动会话与接力的互斥（.slice-lock 会话锁）

接力任务和你自己的手动会话可能同时推进同一仓库的切片（2026-09-02 实测撞过一次：接力把手动会话未提交的验收中状态当作「没人管的半成品」接管了）。防护机制是仓库根的 `.slice-lock` 文件：

**规则**

- 文件三行：第一行属主（`manual` 或 `relay`）、第二行会话/运行标识、第三行 ISO 时间戳
- **手动会话开始推进切片前**：写入 `.slice-lock`（`manual` + 会话标识 + 当前时间）；收工或暂停时删除
- **接力每轮触发先查锁**：
  - `manual` 锁且 < 6 小时 → 安静退出（你在干活，它不抢）
  - `manual` 锁 ≥ 6 小时 → 仍退出，但简报提醒你删锁（防忘记解锁卡死流水线）
  - `relay` 锁 ≥ 3 小时 → 上一轮接力异常死亡，刷新锁后接管继续
  - `relay` 锁 < 3 小时 → 另一轮接力在跑（异常），安静退出
  - 无锁 → 写锁后开始工作，**结束（含中途退出）必须删锁**
- 工作区有未提交改动且无锁 → 接力安静退出，绝不接管不明归属的半成品
- `.slice-lock` 已加入 `.gitignore`，不会被提交

**给你的操作建议**：让我手动推进切片时说一声「手动推进」，我会先写锁；如果你自己用别的 AI 工具改仓库，也建议随手建一个 `.slice-lock`（内容随意三行即可），接力就会让路。

## 7. 故障速查

| 现象 | 原因与处理 |
|---|---|
| 「本轮执行已达到步骤上限」 | 单轮步数安全阀，不是错误。手动会话回「继续」；接力任务下一轮自动接上 |
| prisma generate 报 EPERM | Windows 下 DLL 被 dev server / 残留 node 进程锁定。停掉占用进程后重试即可 |
| 执行器日志停在半路无交付报告 | 进程被杀（宿主重启等）。检查 git 状态判断完成度，补齐后重跑验收或直接修订轮 |
| Git Bash 里 pnpm/opencode 路径串扰 | 用 `cmd.exe //c` 调用；runner 内部已是 cmd 调用，不受影响 |
| lint 基线暴增 | 检查是否误用带 `--fix` 的 lint 变体改了源码——验收一律用 `lint:check` |
| 接力与手动会话撞车 | 已有 `.slice-lock` 互斥（见第 6 节）；若接力简报说「手动会话持锁」，删 `.slice-lock` 即可放行 |
| 接力简报反复「安静退出」 | 检查 `.slice-lock` 是否遗留（手动删）、`logs/oc/` 是否有卡住的执行器进程（杀掉并清理半成品） |
