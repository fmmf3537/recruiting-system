# F4-S1 起草前停点：PRD 规则表 vs 代码现状冲突清单（待拍板）

## 冲突 1：规则「推荐到用人部门（推进到『部门筛选』）+5」——「部门筛选」阶段不存在

- **PRD**：6.2 规则表「推荐到用人部门（推进到「部门筛选」），数据来源 StageRecord，+5，同一候选人只记一次」。
- **代码现状**：系统阶段已在「招聘流程模板」切片后**模板化**，全局兜底常量 `STAGE_ORDER = ['入库','初筛','复试','终面','拟录用','Offer','入职']`（server/src/constants/index.ts:2），seed 默认模板同值（server/prisma/seed.ts:27）。全代码库**不存在**「部门筛选」阶段名；且不同职位类型可配不同模板，任何硬编码阶段名都不可靠。
- **可选方案**：
  - A. 映射为「首次推进离开『入库』」（即候选人第一次产生新 StageRecord 时记 +5）——语义最接近「HR 筛完推荐给用人部门」，且与模板解耦。**推荐**。
  - B. 映射为固定阶段「初筛」——简单，但模板不含「初筛」时该规则永不触发。
  - C. 规则字典加「触发阶段名」配置项（remark/description 存阶段名），管理员按模板自配——灵活但 F4-S1 复杂度上升，且跨模板语义仍模糊。
- **请你拍板**：A / B / C，或其他定义。

## 冲突 2：规则「入职后试用期淘汰 -20」——系统无「试用期」数据模型

- **PRD**：6.2「Offer 被拒 / 入职后试用期淘汰，-10 / -20，数据来源 Offer.result / 阶段回退」。
- **代码现状**：全代码库无「试用期」字段或状态（grep 0 命中）。唯一相关能力：`advanceStage` 允许 **admin** 回退阶段（非 admin 禁止回退，candidate.service.ts）；「入职」阶段记录也可被置为 rejected。
- **可选方案**：
  - A. 触发点定义为「候选人已到达『入职』阶段后，admin 将阶段回退或把入职阶段置为淘汰」→ 记 -20。**推荐**（无需新模型，覆盖「入职后反悔/试用不合格」的管理动作）。
  - B. 本期不实现该负分规则：字典内置该规则但默认 disabled，待试用期模型上线再启用。
- **请你拍板**：A / B。

## 冲突 3：规则「候选人入职（阶段→已入职）+50」——「已入职」判定存在两个信号

- **PRD**：「候选人入职（阶段→已入职），数据来源 StageRecord，+50」。
- **代码现状**：入职有两条路径且会**同时**发生——
  1. `Offer.result=accepted` → 自动 `joined=true` + 自动推进候选人到「入职」阶段（offer.service.ts:282-294）；
  2. `markJoined` 接口（要求 result=accepted）→ `joined=true`（offer.service.ts:630-646）。
  另有 admin 直接 `advanceStage` 到「入职」阶段的手工路径。
- **可选方案**：
  - A. 触发点 = 「候选人产生『入职』阶段的新 StageRecord」（三条路径最终都会落到 StageRecord，天然统一；幂等靠唯一约束）。**推荐**。
  - B. 触发点 = `Offer.joined` 置 true 时——会漏掉 admin 手工推进路径，且与 StageRecord 双写时要防重。
- **请你拍板**：A / B。

## 偏差 4（非冲突，拟按默认实现，若无异议随上面一并确认）：「猎头渠道简历处理 +3」的触发点

- **PRD**：数据来源写的是 `AgencySubmission 审核通过/推进`；F5-S 按安全复核未建 AgencySubmission 表（候选人本体即记录）。
- **拟默认实现**：猎头来源候选人（`source` 以 `猎头:` 开头）**首次推进阶段**时记 +3（与冲突 1 的 +5 不叠加：猎头候选人首次推进只记 +3 不记 +5，防灌水——这也正是 PRD 两条规则分列的意图）。同一候选人靠 `@@unique([userId, ruleCode, targetType, targetId])` 幂等只记一次。
- **请你确认**：同意 / 另给定义。

## 无冲突已核实项（供安心）

- 考核对象 role=hr：代码 `normalizeUserRole` 已把历史 member 归一为 hr（role-permission.service.ts:53），按 PRD 执行无冲突。
- 「简历上传并解析成功 +2」：`Candidate.createdById` 成立，猎头渠道按 `source` 前缀排除即可。
- 「完成一场面试 +10」：Interview 有 status 状态机与 `createdById`，完成事件可挂。
- 「发出 Offer +30」：Offer 有 `sent` 状态（审批流），事件点明确。
- 「Offer 被拒 -10」：`OfferResult.rejected` 存在，事件点明确（注意与「发出 Offer」同人同日可能并存，PRD 已允许正负并记）。
- 幂等模型：PRD 给的 `@@unique([userId, ruleCode, targetType, targetId])` 与 Postgres 唯一索引兼容（nullable target 列在多行 NULL 场景不冲突，业务事件均带 target）。
